# Shared Cargo output can change before same-source payload packaging

Reviewed commit: 00de0b6c9cf206f1a7c9c5ad1c76b5b10eaf85db

## TLDR

Source-confirmed review record: concurrent builds in supported separate checkouts sharing CARGO_TARGET_DIR can make the new payload producer package another checkout's Farhelm executable. The real tests can then reject a mismatched protocol or exercise a payload from a different source revision than the one their evidence names. This is a maintainer validation-input race, not an observed test failure, guaranteed false pass or user-work/security consequence. Source route: script:29-36 builds into the chosen shared target directory and stores the unversioned <target-triple>/debug/farhelm path. After Cargo exits, :37 invokes build-pinned-tmux-ci.sh before :38 checks the ELF and :47 copies that Farhelm path into the private stage. A cold tmux cache runs a separate venv/pip installation and C build (same-revision build-pinned-tmux-ci.sh:53-78), providing an actual intervening task rather than requiring an arbitrary pause at a tiny instruction window. A second checkout's native musl cargo build can finish during that interval and publish its own farhelm at the same final path; for example, same-revision test-provision-centos.sh:59-65,260-267 honors the same CARGO_TARGET_DIR and builds that target/package. A correct static ELF from that other revision passes the producer's architecture/static check. .agents/machine.md:20-26 explicitly permits shared Cargo target directories across separate workspaces because Cargo locks; this interleaving obeys the one-command-per-checkout contract. Pinned-tool source premises were checked, not assumed from an unrelated Cargo version. rust-toolchain.toml at the reviewed revision

# A pending container approval follows a retargeted host to another machine

Reviewed commit: 190d844e58c96cf197aa838d0b0eea8062f48435

## TLDR

A user can approve an agent's card naming one container host and have Farhelm create the container, run its command and deliver the recipe's credentials on a different machine. Changing the host's SSH destination while the card waits does not invalidate it; the launch uses the changed destination after a fresh Podman check.

## Details

The route is a first container launch at an ordinary SSH place that has a usable Podman probe but no existing environment rows or recipe images/helpers. An ordinary agent issues create --recipe <recipe> --container-host <host>. plan_environment_create resolves the name into Place::PodmanHost(id) (agent_requests.rs:4180-4209). launch_environment_for_agent reads the display name before approval (4485-4491), then freezes that old name and numeric place in ApprovalAction::LaunchEnvironment (4493-4515), with the resolved command and launch fixed. No destination, entry UUID, connection or BaseRoute snapshot for the container PLACE is retained. The card can remain pending while the operator changes that SSH row's destination in Hosts. hosts.rs:1121-1165 calls store.update_ssh_destination; store.rs:7521-7599 permits an ordinary SSH retarget after store/podman.rs:215-253 verifies no environment/resource references. Pending cards are not among those references, and the agent has not registered an environment yet. A recipe with no images at this place is valid because Podman builds lazily: RecipeState::require_launch_source does nothing for Podman (environment/recipes.rs:259-268).

After refreshing that row's Podman probe for the new endpoint (hosts.rs:1669; podman_probe.rs:435-477), Allow still succeeds: approvals.rs:435-570 tracks only the requesting session/connection, and approved at agent_requests.rs:2865-2893 rechecks only that origin. The only extra target recheck here is for a clone source (4519-4528), absent on create. The handler passes the same numeric place to start_session_environment at 4541-4550. That task validates CURRENT provider availability and registers the row (provisioning/tensorlake_add.rs:346-400), then ensure_prepared and all commands resolve the place's CURRENT endpoint (environment/podman.rs:148-188,950-1033). They compare against the current probe, not the route the card named. A refreshed success for machine B therefore admits launch on B while the card still names A. Source-side environment ownership/admission guards do not compare A and B because this launch has no prior resource.

The credential consequence is present in shipped code, not hypothetical additional functionality: environment_session_steps calls delivery.setup with this recipe at provisioning/tensorlake_add.rs:597-605. credential_delivery.rs:347-368 applies the recipe, resolves the new environment's current access route at 434-440, and installs a configured Codex login at 575-609 or recipe GitHub token at 614-654. Those secrets are now inside a container on B. The operator's separate retarget action does not answer or redraw the pending agent confirmation that still names A.

Contract: SPEC_impl.md:9548-9556 says ‘What a card shows is what an approval does’ and ‘A launch is also refused if the target host's connection changed while the card waited, since the approval was for the machine the card named.’ SPEC.md:4330-4332 specifically requires the environment card to name where the environment will be created. SPEC_impl.md:1071-1074 requires answered controls to act on what was drawn. The recipe/place encoding being separate from an installed-host identity (6506-6509) specifies reusable placement, not permission for a confirmation to silently follow a changed physical endpoint. Keep the place route/entry snapshot with the planned launch and reject a mismatch after Allow under admission that cannot race the destination writer; alternatively invalidate the old card and ask for the new target.

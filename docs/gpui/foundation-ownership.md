# GPUI foundation ownership

Each app-wide concern of the GPUI app has one owner (SPEC_impl.md, "GUI architecture"). This table says which paths each
owner holds, and which of them are extension points: places an area may add to without asking, as long as the addition
follows the pattern already there. Every other change to an owned path is requested through the orchestrator (a
foundation-change request in the area's outbox), never made directly by an area. The lint exceptions column counts the
`#[allow]`s that let an owner make the one call `crates/gui/clippy.toml` bans everywhere else.

The table covers every foundation file as milestone M1 left them. From M1 on, the landing step of every area PR runs
`scripts/check-foundation-paths.py`, which refuses the PR when it touches an owned path in a way no extension point
admits; a foundation PR made by the owner runs it with `--owner`, which reports the same findings without refusing.

This file is the check's only source. It reads each foundation's owned paths from the main table's second column (the
backticked paths there) and the rules from "Extension point rules" below, always from the base revision's copy of this
file, so a PR cannot widen the rules it is judged by. For the same reason the landing step runs the base's copy of the
script, from stdin, after rebasing the PR onto that base:

    git show <base>:scripts/check-foundation-paths.py | python3 -I - --repo <checkout> --base <base> --head <PR commit>

`--head` is the PR's commit id or bookmark, never `HEAD`: in a jj workspace git's `HEAD` is the working copy's parent,
which need not be the PR's tip. Every path the tables name must exist in the base revision, so an owner who renames a
foundation file updates the table in the same PR, or the check stops.

Paths are relative to the repository root; a path ending in `/` covers everything under it.

## What is not a foundation

The rest of `crates/gui/farhelm-gui/src/` is area code, owned by the area that builds it and outside this table: the
session list (`session_list.rs` and `session_list/`) belongs to the sidebar area, the session pane (`session_pane.rs`
and `session_pane/`) to the session-view area, and the terminal (`terminal.rs` and `terminal/`) to the terminal area.
The reference PNGs under `crates/gui/farhelm-gui/tests/goldens/` and the screenshot scene list
(`docs/gpui/screenshot-scenes.json`) are outside it too: an area adds its own scenes and references and updates them,
with no request and no rule from the check.

## Extension point rules

The landing-step check knows two rules. `new-files` sits on a directory and admits only files the diff adds under it;
changing or deleting a file already there is refused. `append-only` sits on a file and admits a change that adds at
least one line and removes none, so a changed line (a removal plus an addition), a binary change, a mode change on its
own and the file's deletion are refused. A rename counts as the deletion of its old path and the addition of its new
one. Where one extension point sits inside another (`components/mod.rs` inside `components/`), the more specific one
decides.

A rule admits a shape of change, not its content. `append-only` on `theme.rs` cannot tell a palette token from any other
added line, so review still checks that an admitted addition follows the pattern the table describes, and an addition
that does not is a foundation-change request even though the check let it through.

The Host text and Drafts extension points have no row here, because they are uses of the foundation from area code (a
view calling `HostText::from_host`, an editor holding a `Draft`) and touch no owned path. The Test harness's reference
PNGs are not owned, so only the golden scene in `goldens.rs` needs a rule.

NOTE: An append-only file only works as an extension point when an addition to it leaves every existing line alone. The
lists areas append to (`Icon::ALL` in `assets.rs`, `SCENES` in `goldens.rs`, `HarnessGlyph::ALL` in `marks.rs`,
`ONCE_PER_PRESS` in `actions.rs`) are slices with one entry per line for that reason; a length in their type changed
with every addition. Two traps remain, and both refused real PRs. Extending a grouped `use` statement
(`use crate::actions::{DeleteSession, RenameSession};`) rewraps it, so an area adds a separate `use` line instead, which
rustfmt leaves alone. Adding to a wrapped doc paragraph (the scene list in `goldens.rs`'s module docs, say) rewraps it
too, so an area adds its own sentence or doc line instead.

# UI: a round, eight-tooth Settings gear

Written against main at 462b0268 on 2026-10-29. This is a goal file for an unattended run, executed through the planning
system in `plans/AGENTS.md`. You, the executing agent, have none of the conversation that produced it; everything you
need is here or in the repository files it names. SPEC.md and SPEC_impl.md stay authoritative over anything this file
says, except where this file records a change the maintainer approved; that change is yours to make in the spec.

## The goal

The TODO.md entry (bucket "Near term"), verbatim:

> - **Fix the Settings gear icon's squished shape.** The gear glyph in `crates/farhelm-ui/src/icons.rs` (`SettingsIcon`)
>   is drawn wider than tall — its outline spans x 0..14 but only y 2.2..13.5 inside the 16×16 viewBox — so it renders
>   as an ellipse rather than a circle. Redraw the path so the silhouette is circular with evenly spaced teeth (equal
>   horizontal and vertical extent).

### What changes

`SettingsIcon` is redrawn as an eight-tooth gear centred in its 16×16 box, exactly as wide as it is tall, with a round
hole in the middle. It sits beside the rail foot's **?** button (`HelpIcon`), whose circle has radius 6.6 around (8, 8);
the gear's tooth tips reach about 6.8 from the same centre so the two read as one pair.

### What does not change

Every place the gear is used (`app_bar.rs`, `settings.rs`, `hosts.rs`), its existing rendered sizes (16 px in the rail
foot and the Settings dialog header, 14 px in a host's row menu through `.menu-icon`), the stroke weight (1.2),
`currentColor`, round caps and joins, `aria-hidden`, and the buttons that supply its accessible name. The
`HostIcon::Gear` host mark (the spoked gear a user can pick for a host) is a different glyph and stays as it is.

### Acceptance criteria

- The gear's outline has equal horizontal and vertical extent (to within 0.05 viewBox units), is centred on (8, 8) in a
  `0 0 16 16` viewBox, and has eight evenly spaced teeth and a round centre hole.
- It renders cleanly at every place it is used, including the 14 px host row menu, where eight teeth are tightest.
- A Rust unit test pins the square, centred silhouette, so a future redraw cannot squash it again without a failing test
  (a planner proposal, kept because it is cheap; see Requirement sources).
- A changelog fragment (`kind: fixed`, for a `fix` PR).
- The TODO.md entry quoted above is removed.

### Resource watchdog

Right after the resume protocol, and before the first sub-agent, build or test run, start a resource watchdog as a
background process (not an agent) and keep it running for the whole run. Every 60 seconds it samples free space on the
filesystems holding the checkout, any jj workspaces you create, the agent scratch directory and `/tmp`, plus available
memory and swap (`df`, and `free` or `/proc/meminfo` on Linux; `vm_stat` and `sysctl` on macOS). It writes each sample
to a private heartbeat/status file in the scratch directory, and it emits a notification when any of these happens:

- a watched filesystem drops under 10% or under 5 GB free, or available memory drops under 10%, whichever comes first;
- the number keeps falling;
- the condition recovers;
- the monitor itself fails.

In Claude Code a notification is a stdout line of a monitor started with the Monitor tool; elsewhere, the harness's
equivalent. A file update alone is not a notification.

Before relying on the watchdog:

- verify delivery with a harmless synthetic alert;
- verify failure detection by killing a throwaway monitor and confirming you are told;
- if you omit periodic heartbeat checks, also stall a throwaway monitor without killing it and confirm you are notified
  within two sample intervals, since a monitor cannot detect its own sampling loop hanging.

If any of these notifications is unavailable or unverified, say so in the log and check the status file at least once a
minute.

On every path, check heartbeat freshness before each new build, test run, sub-agent or review launch. A dead monitor, or
a heartbeat stale for two sample intervals, pauses new launches until monitoring is restored; restart a dead watchdog.

An alert is an instruction to act:

1. stop launching sub-agents and work;
2. remove jj workspaces, build output and scratch you own that are no longer needed;
3. wait for or stop the job most likely responsible;
4. resume only when the watchdog reports headroom.

Record the watchdog's handle, watched paths, status path and delivery mechanism in the log. Include its state in every
handoff note so a resumed session reconciles or restarts it, and stop it when the plan closes. Do not lengthen the
sampling interval to save turns.
